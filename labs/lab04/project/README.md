# Лабораторная работа № 4 — Эмуляция и измерение задержек в глобальных сетях

**Дисциплина:** Моделирование сетей передачи данных  
**Тема:** Эмуляция и измерение задержек в глобальных сетях (NETEM, Mininet)  
**Среда выполнения:** Mininet VM (Ubuntu 20.04), Python, `tc netem`, GNU Make, Gnuplot, `ping`.

## Цель

Исследовать влияние задержки, вариации задержки (jitter), корреляции и распределения задержки на время приёма-передачи (RTT) в виртуальной сети Mininet. Выполнить воспроизводимые эксперименты, сохранить измерения, построить графики и вычислить статистику.

## Топология

Два виртуальных хоста `h1` (`10.0.0.1`) и `h2` (`10.0.0.2`) подключены к одному коммутатору `s1`. Управляющий узел — `c0`. Эмуляция производится через Linux `tc` с дисциплиной `netem` на интерфейсах хостов.

## Структура проекта

```text
project/
├── simple-delay/        # Постоянная задержка 100 мс на каждом хосте
├── change-delay/        # Сравнение 100 и 50 мс на каждом хосте
├── jitter-delay/        # Задержка 100 мс с вариацией 10 мс
├── correlation-delay/   # Задержка 100 мс, вариация 10 мс, корреляция 25%
└── distribution-delay/  # Задержка 100 мс, вариация 20 мс, нормальное распределение
```

В каждом каталоге находятся:

- `lab_netem_i.py` — Python-скрипт, создающий сеть, задающий параметры NETEM и выполняющий измерения;
- `Makefile` — автоматический запуск эксперимента, генерация графика и статистики;
- `ping_plot` — скрипт Gnuplot для построения `ping.png`;
- `ping_stats.py` — расчёт числа наблюдений, минимума, среднего, максимума и стандартного отклонения RTT;
- `ping.dat` и `ping.png` — данные и график завершённого запуска (в каталоге `change-delay` вместо `ping.dat` используются `ping_100.dat` и `ping_50.dat`).

## Воспроизведение

Запускать **в виртуальной машине Linux с Mininet**, а не в обычной командной строке Windows. Необходимы работающие Mininet, `tc`, `ping`, `python` (доступный в системе Python с установленным модулем Mininet), `python3`, Gnuplot и GNU Make, а также права `sudo`.

Для отдельного эксперимента перейдите в соответствующий каталог и выполните:

```bash
make
```

Эта команда запускает Python-сценарий, формирует данные, строит PNG-график и выводит статистику. Повторный запуск с уже существующими файлами может ничего не пересчитать; при необходимости использовать цель `clean`, учитывая, что она удаляет сохранённые `.dat` и `.png`:

```bash
make clean
make
```

**Важно:** оставьте исходные измерения и графики из выполненной работы в репозитории; очистку выполняйте только при осознанном повторном запуске. В случае `change-delay` один запуск формирует два файла результатов и один сравнительный график.

## Измеренные результаты

Ниже приведены **реальные результаты отдельных запусков**, полученные при выполнении ЛР-4. Они могут меняться при повторении вследствие случайности NETEM и нагрузки виртуальной машины. Для всех перечисленных результатов рассчитано стандартное отклонение (`statistics.pstdev`) по значениям RTT в файлах данных.

| Эксперимент | Измерений | Мин., мс | Сред., мс | Макс., мс | Станд. откл., мс |
|---|---:|---:|---:|---:|---:|
| `simple-delay`: 100+100 мс, повторный запуск | 100 | 200.000 | 219.930 | 420.000 | 32.083 |
| `change-delay`: 100+100 мс | 100 | 200.000 | 215.960 | 644.000 | 48.885 |
| `change-delay`: 50+50 мс | 100 | 101.000 | 109.640 | 185.000 | 13.124 |
| `jitter-delay`: 100±10 мс на h1 | 100 | 91.700 | 107.499 | 227.000 | 16.206 |
| `correlation-delay`: 100±10 мс, 25% на h1 | 100 | 90.800 | 108.485 | 243.000 | 19.297 |
| `distribution-delay`: 100 мс, вариация 20 мс, normal на h1 | 100 | 49.900 | 107.960 | 188.000 | 23.490 |

Задержки вида `100+100 мс` задаются на исходящих интерфейсах обоих хостов и приводят к ожидаемому RTT порядка 200 мс. В остальных трёх сценариях NETEM применяется только к `h1-eth0`.

## Интерпретация

- При снижении двусторонней заданной задержки со 100 до 50 мс на хост средний RTT снизился с 215.960 до 109.640 мс.
- В опытах с вариацией, корреляцией и нормальным распределением RTT колебался относительно заданной задержки.
- Отдельные большие значения RTT могут быть связаны с дополнительными задержками виртуальной среды; они не доказывают неправильность настройки NETEM.
- Указанные 25% — **заданный параметр корреляции NETEM**, а не коэффициент, независимо оценённый по измерениям.
